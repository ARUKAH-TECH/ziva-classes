# ZIVA Online & Special Classes Management System (SCMS)

Role-based education management platform for ZIVA Online & Special Classes — admin, teacher, parent, and optional student portals, built on Next.js + Supabase.

## Status

- **Phase 1** — project scaffold, ZIVA design system, Supabase auth wiring, role-based dashboard shells.
- **Phase 2** — admin CRUD: organization profile + policy toggles, academic years/terms/levels, subjects, classes (with subject assignment), teachers (with account provisioning), and teacher class/subject assignments.
- **Phase 3** — parents module (account provisioning), full student management (create, profile tabs: Overview/Photo/Location/Subjects/Parents), passport photo upload with server-side compression + private signed-URL delivery, location history (current + preserved past locations), parent-child linking, and the Parent Dashboard wired to real linked children.
- **Phase 4** — Timetable (recurring weekly `class_schedules`, constrained to real teacher assignments), a "generate sessions from schedule" action that materializes dated `class_sessions` (snapshotting location for single-student Home Service sessions per Rule 11), and session-based Attendance with the photo-beside-name roster UX for both Admin and Teacher. Attendance % is now computed live everywhere it's shown (Parent Dashboard, Student Overview, Admin Dashboard) from actual attendance rows — never a manually entered figure, per §18.
- **Phase 5** — Grading Scales admin UI (Settings > Grading — one scale per academic level, with configurable grade bands, finally giving the `002_amendments.sql` grading tables a UI). Assessments (Assignment/Quiz/Test/Examination/Project) creatable by both teachers (own class/subject only) and admins (any real teacher assignment). Score entry with automatic grade lookup against the student's level's active scale. Results/performance dashboards for both roles. Academic average is now real everywhere it's shown (Parent Dashboard, Student Overview) — computed from actual scores, same principle as Attendance.
- **Phase 6** — Fees & Payments (`/admin/fees`): per-subject/class Fee Structures, a "generate charges" action that materializes `student_charges` from active structures for every actually-enrolled student in a term, payment recording restricted to MTN Mobile Money / Cash only (Rules 7-8 — grepped the codebase to confirm GCB never appears), with allocation across a student's outstanding charges (auto-fills oldest-first, adjustable). New Student "Fees" tab (charges, balance, payment history). Financial dashboard (Total/Today's/Monthly Collection, Outstanding Fees, MTN MoMo vs Cash split, Revenue by Subject/Class). Admin Dashboard and Parent Dashboard now show real fee figures instead of placeholders.
- **Phase 7 — Terminal Report engine (core module, §20-31)**. `src/lib/reports/compute-report.ts` computes the entire report (per-subject scores/grades via the Phase 5 grading scales, overall average/grade, strongest subject, areas for improvement, optional ranking among classmates, term-scoped attendance, fee status) from live records — never manually calculated. Draft → Publish → Archive versioning: publishing freezes a `snapshot_data` JSONB payload and locks comment edits; regenerating after publish creates a new version rather than mutating the published one; the old published version is auto-archived. Admin UI at `/admin/terminal-reports` (class+term picker, bulk "Generate all," per-report Publish/Unpublish/Edit comments) and a print-styled `TerminalReportView` (blue/white/gold, official logo, A4-ready, `print:hidden` app chrome for clean browser printing). PDF export via `@react-pdf/renderer` at `/api/terminal-reports/[id]/pdf`, access-gated entirely by the same RLS as everywhere else. Parent and Student portals get read-only published-report views. Two real bugs caught and fixed during review: `ranking_enabled` wasn't threaded through on recompute/publish, and subject averages weren't scoped to the report's academic year.

- **Phase 8** — Educational Needs/Interventions (teacher flags a need with priority + parent-visibility toggle, adds interventions, admin oversees status); Communication (org-wide Announcements, direct Messages between admin/teacher/parents with a simple inbox); Notifications (`notifications` table, mark-read) wired as real triggers on attendance absence, score upload, terminal report publish, and an admin-initiated fee reminder; and the parent change-request approval queue that had been designed back in Phase 2/3 but never actually built out — `/parent/children` (a nav route that had pointed nowhere until now) with location/photo "request a change" flows gated by org settings, and an admin approval banner right on the student's Location/Photo tabs. Three real RLS gaps found and fixed in `database/005_messages_rls_fix.sql`: no UPDATE policy existed for `messages` at all (mark-as-read silently no-op'd), teachers had zero visibility into `parent_students`/`parent_profiles` needed for messaging parents, and the supplied `needs_parent_view`/`interventions_parent_view` policies never actually checked `visible_to_parent` — internal-only notes were only being hidden by application code, not the database, contradicting §38.

- **Local dev + role-by-role testing pass** — first time this app was exercised end-to-end against a real (local) Supabase instance rather than just type-checked. Found and fixed three chained RLS infinite-recursion bugs that made every single admin "create student" call fail (`database/006`-`008`), a teacher-facing page (`/teacher/assessments`) that 500'd because it called an admin-only server action for a plain read (fixed by adding `requireOrgMember`, a read-only guard matching what RLS's own `*_org_access` policies already permit), and a missing `teacher_profiles` parent-visibility policy that silently nulled out teacher names on parent-facing pages (`database/009`). Also built out five nav links that existed in the sidebar but 404'd — `/teacher/classes`, `/teacher/subjects`, `/teacher/profile`, `/parent/profile`, `/parent/timetable` — each backed by a real server action, not a stub. (The remaining broken links from this pass were closed out in the two follow-up entries below.)

- **Student portal + account provisioning** — the Student role existed in the schema/permissions since Phase 1 but had no way to ever sign in: no admin UI created a student login the way `/admin/teachers`/`/admin/parents` do for the other roles. Added an **Account** tab to the admin student detail page (`provisionStudentAccount`, same temp-password-reveal pattern as teacher/parent creation) and built out the remaining six student nav routes — `/student/subjects`, `/student/timetable`, `/student/attendance`, `/student/results`, `/student/assignments`, `/student/profile` — plus rewired `/student/dashboard`, which had shipped as an all-placeholder static shell, onto real data. Required three more missing RLS student-view policies (`database/010`, `011`) — `assessments`, `class_schedules`, and `class_sessions` had `*_parent_view`/`*_teacher_view` policies but no student equivalent, so a signed-in student got zero rows back, silently. Verified end-to-end with seeded data: a real assignment created as JHS 2 Mathematics, graded, and confirmed showing correctly on both the student's Assignments and Results pages — not just empty-state screenshots. Caught and fixed one more bug in the process: the Account tab's post-creation temp-password reveal never actually rendered, because the server-revalidated `hasAccount=true` prop and the local `created` state landed in the same render and the wrong one had priority — the admin would create a working login and then never see the password to hand to the student.

- **Remaining nav gaps closed** — the last five 404ing links. `/admin/reports`: a new cross-cutting per-class table (enrollment, attendance rate, academic average, fee revenue) distinct from the existing Dashboard/Results/Fees pages, backed by a new `getAttendanceOverviewByClass()` (org-wide, all-time — the Dashboard's attendance figure is "today only"). `/teacher/students`: every student across a teacher's actual class/subject assignments, deduplicated, via a new `listMyStudents()`. `/parent/attendance`, `/parent/performance`, `/parent/fees`: per-child views across every linked child, reusing existing role-agnostic RLS-scoped functions (`getStudentAttendanceSummary`, `getStudentPerformanceSummary`, `listStudentCharges`, `listPayments`) that already worked for parents — no new RLS policies needed for these three, unlike every other round. Verified end-to-end with seeded fee charges, a payment, and an attendance record, not just empty states. All previously-broken nav links across every role are now real pages.

See `docs/architecture-plan.md` for the full roadmap. `npm run build` and `npx next lint` both pass clean.

## Getting started

1. **Create a Supabase project**, then in the SQL editor run, in order:
   - `database/schema.sql` (supplied source-of-truth schema)
   - `database/rls_policies.sql` (supplied RLS policies)
   - `database/002_amendments.sql` (grading scales, org settings, parent change-request queue, photo path rename, terminal report snapshot columns)
   - `database/003_rls_org_scoping_fix.sql` (closes a cross-tenant gap in the supplied admin RLS policies — see comments in the file for why)
   - `database/004_storage_policies.sql` (creates the private `student-photos` bucket and its access policies — the supplied RLS only described these in comments, no actual bucket/policies existed)
   - `database/005_messages_rls_fix.sql` (adds a missing `messages` UPDATE policy, teacher visibility into `parent_students`/`parent_profiles` for messaging, and enforces `visible_to_parent` at the RLS layer for student needs/interventions — see comments in the file for why)
   - `database/006_fix_student_rls_recursion.sql`, `007_fix_parent_students_rls_recursion.sql`, `008_fix_parent_profiles_rls_recursion.sql` (three chained "infinite recursion detected in policy" bugs — pairs of RLS policies subquerying each other's table — that broke every admin "create student + enroll + link parent" call. Fixed with `SECURITY DEFINER` helper functions, same convention as `is_admin()`. See comments in each file for the exact policy pairs.)
   - `database/009_teacher_profiles_parent_view.sql` (adds the missing `teacher_profiles` SELECT policy for parents — without it, a child's teacher's name silently came back null on any parent-scoped view that joins through it, e.g. the parent Timetable page)
   - `database/010_student_view_policies.sql`, `011_teacher_profiles_student_view.sql` (adds the missing student-facing SELECT policies on `assessments`, `class_schedules`, `class_sessions`, and `teacher_profiles` — a signed-in student got zero rows back from any of these, silently, until now)
2. Copy `.env.local.example` to `.env.local` and fill in your Supabase project URL/keys, **including `SUPABASE_SERVICE_ROLE_KEY`** (required for admin-provisioned teacher/parent accounts).
3. Install dependencies and run the dev server:
   ```
   npm install
   npm run dev
   ```
4. Create your first Super Admin user directly in Supabase Auth, then insert a matching row into `public.users` with `role = 'SUPER_ADMIN'` and the correct `organization_id`.

## Project structure

- `src/app/` — Next.js App Router routes, grouped by role: `admin/`, `teacher/`, `parent/`, `student/`, plus `(auth)/login` and `(auth)/register`.
- `src/components/ui/` — base design-system primitives (Button, Card, Input, Alert, EmptyState, ...).
- `src/components/domain/` — ZIVA-specific components (ZivaLogo, StatCard, ...).
- `src/components/layout/` — Sidebar, Header, MobileNav, DashboardShell.
- `src/lib/supabase/` — browser + server Supabase clients.
- `src/lib/permissions/` — role/nav config (UX convenience only — RLS is the real security boundary).
- `src/middleware.ts` — session refresh + role-based route redirect.
- `database/` — schema, RLS, and amendment SQL files (source of truth).
- `docs/architecture-plan.md` — full architecture/design deliverable.
